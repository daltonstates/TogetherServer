# TogetherServer 0.3.2 release

Date: 2026-10-09. The owner explicitly authorized a new release numbered **0.3.2**. Release preparation is in progress; this document will record the verified source, Windows run and public asset hashes after publication. The owner's running app and data are preserved.

## Changes

- Start or Stop is the primary Host action above the server tabs; running-server connection details lead Overview. Create and Join have equal first-use actions, and Friend Play leads with starting, opening the game and connection details.
- Secondary diagnostics and server tools use named disclosures. Players prioritizes the count and empty-server timer. Server tabs use icons and a common inset, including padded Sessions filters and results.
- Chat Sync immediately shows pending feedback and then success or failure. Success feedback is short lived and late results from another server or connection are cancelled.
- Native executable, window and tray icons use embedded multi-size assets rather than a temporary drawing.
- Successful action receipts expire after eight seconds or retire as soon as newer server evidence supersedes them. A Ready server no longer retains the original waiting-for-startup result in its header or Notifications. Friend startup/Stop receipts follow the same rule; pending actions and errors stay visible.

Implementation and source/synthetic evidence are recorded in [the core UX delivery](19-CORE-UX-DELIVERY.md). No lifecycle, process identity, permission, pairing or world-save authority was changed by these UX fixes.

## Compatibility and release checks

Application, UI manifest and root lockfile versions are aligned to 0.3.2. Companion protocol remains 3, storage schema 4 and pairing schema 3.

The Windows workflow builds one source-stamped candidate and shares those exact bytes across Existing, QolApi, Browser, Desktop and Rehearsal lanes. Separate compatibility runners test the actual hash-pinned published 0.3.0 and 0.3.1 binaries in both Host/Friend directions and in the updater handoff. Version assertions use the candidate's current version; legacy versions remain an explicit allowlist. Checkpoints retain the exact previous executable and validate the expected source schema, settings and resulting schema.

Release-check maintenance corrects only obsolete first-use/header selectors and removed timer wording. The action, protected-draft, permission, timer and screenshot assertions remain enforced.

Local validation passed 687/687 JSDOM tests across 66 files and the complete code-only gate: locked dependency restore/install, TypeScript, lint, zero-warning/error solution compilation, 20 source/synthetic groups, whitespace and diagnostic isolation. Native-import symbolic-link subcases remain skipped because the account cannot create those links. The first code-only invocation stopped on a Git CRLF warning; the edited source was normalized to the repository's required LF and the final complete invocation passed. Logs are retained in ignored `local-data/release-0.3.2/`.

The [first 0.3.2 Windows run](https://github.com/daltonstates/TogetherServer/actions/runs/38019757558), source `21b7ac5a283378924683d51bf40736ca0c1ca67d`, exposed a browser-harness timing fault. Backend state was confirmed Offline, but the direct manual-backup API can publish a temporary world-copy reservation to a three-second UI poll. Restore review completed within 764 milliseconds, before that UI evidence refreshed, so its offline guard correctly kept Restore disabled. The harness now waits for the selected Host's visible Offline state after Stop and again before reviewing Restore following the backup. Disabled-before-confirmation, enabled-after-confirmation, cancelled Restore and both unchanged-world sentinels remain enforced. Runtime guards and polling were unchanged. This failed run is not publication acceptance; the complete workflow must pass for the next source-stamped candidate.

Packaging waits for all verification lanes and compatibility jobs, compiles the installer around the same verified portable bytes, tests install/uninstall on a disposable Windows runner, and emits four public assets with a source/hash manifest. Publication requires matching source identity, asset hashes and completed acceptance; fresh public downloads are checked again after publication.

## Acceptance boundaries

Only code-only, JSDOM, byte/resource inspection and compilation run on the owner's active desktop. App, browser, native, game, process, fixture and installer journeys run exclusively on dedicated hosted Windows runners with explicit opt-in and disposable data.

Synthetic loopback and package acceptance do not establish real Friend-PC/WAN reachability, an installed-game join, real-world save integrity or real-game restart recovery. Real-game live save and the existing fixture/preview support boundaries remain unchanged.
