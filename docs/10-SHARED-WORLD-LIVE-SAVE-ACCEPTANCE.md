# Live save sharing acceptance

The real built-in adapters currently describe candidate save controls. **Live capture is disabled for every real game.** Production shares its hash-verified post-Stop backup. The marked staging app additionally offers a fixed owner **Save and share now** action for the synthetic fixture: exact-process nonce completion, bounded immutable staging, signed publication and normal Receive/receipt. This is synthetic evidence only. A command reply, file timestamp, open port, or running process does not establish a complete real save.

The owner interface shows completion, immutable snapshot, other-PC transfer/receipt, game load, recognizable change and saved restart as separate Unverified stages for each real game. The fixture action cannot enable a real candidate. Real staging still rejects mutable-tree scanning even if its command or log candidate matches. An immutable snapshot adapter and a reviewed per-game acceptance entry must both exist before enabling that real game.

| --- | --- | --- |
| Fixture | Enabled only for the exact running staging fixture, sharing opted in, authority/copy work resolved | Packaged process, signed-copy and loopback receipt evidence only; no real game claim. |
| Valheim | Disabled | Bind the run-scoped autosave observation to immutable world bytes; separate-PC load/change/restart. |
| Minecraft Java | Disabled | Trusted completion of fixed save-all flush plus immutable byte binding; separate-PC load/change/restart. |
| Minecraft Bedrock | Disabled | Proven query grammar, held immutable files and resume acknowledgement; separate-PC load/change/restart. |
| Factorio | Disabled | Exact requested ZIP target and completed closed archive binding; separate-PC load/change/restart. |
| Terraria | Disabled | Trusted run-scoped save completion and immutable world binding; separate-PC load/change/restart. |

Pending Bedrock holds now attempt the fixed exact-run resume on app startup and through an owner retry action. Dispatch leaves the durable marker visible and blocks another capture until a verified acknowledgement. Unmatched, changed or stopped processes retain the marker for review. No surfaced action sends hold/query for a real unaccepted game.

The Valheim candidate observes `World save (5/5) done` only as a complete timestamped line appended after a cursor is opened on the exact managed run's owned `-logFile`. Its strict line shape includes the observed `. Total time [Nms]` suffix; this shape came from read-only historical dedicated-server logs and may change with game updates. It checks the saved profile, process ID, start time, executable, operation log path, and Windows file identity; a stale run, another run's cursor, replaced or truncated log, or incomplete or oversized line fails closed. The disposable fixture tests this observation logic. A matched line does not prove a copyable or loadable world. This candidate has no capture, publication, Host/Friend action, or live-sharing acceptance gate.

The Java candidate has an internal exact managed-process console dispatcher and a disposable fixture check. It sends the fixed `save-all flush` text only after the recorded PID, start time, executable, and console members match. The fixture confirms receipt while the process remains running. The dispatcher reports only that the command was sent; it does not report flush completion, create a live snapshot, or publish a shared version. There is no Host or Friend action for it.

The Terraria command candidate is also internal. It accepts only a saved operation ID, reloads the current managed run and Terraria profile, checks the reviewed driver's imported-world and executable validation and declared TCP port, then verifies the exact live PID, start time, executable, and isolated console membership. It sends only literal `save` and always reports `CompletionConfirmed: false`. A disposable Windows `TerrariaServer.exe` fixture check is included for exact-run command routing, rejection cases, and process survival, but its runtime check was skipped while foreground-affecting tests were paused and is not in the automatic release gate yet. That check cannot prove Terraria finished writing, that a copied `.wld` is consistent, or that another game can load it. No Host, Friend, API, UI, or shared-copy publisher calls this candidate, and Terraria `LiveCaptureAccepted` remains false. A future surfaced action would also need Host lifecycle serialization and exact-run completion and load evidence.

The Factorio candidate has an internal dispatcher for the literal `/server-save` command. It requires the recorded Factorio operation, PID, start time, executable, managed save, declared TCP RCON port, and current saved profile to agree before using that profile's existing protected credential with loopback RCON. An internal archive candidate can separately open the reviewed `<world-id>.zip` for an exclusive read, inspect bounded ZIP entries and CRCs, compare source and staged hashes, and keep one read-only copy under app-owned candidate storage for that exact run. This is structural staging only: it does not show that `/server-save` wrote that ZIP, that Factorio selected it instead of another autosave target, that the write completed, or that another game can load it. The dispatcher and archive candidate both report `CompletionConfirmed: false`; no Host/Friend action, shared-copy publisher, or live-capture route calls them. Archive checks are compiled but have not been run while desktop tests are paused. **Factorio live capture remains disabled.**

The Bedrock candidate sends only fixed `save hold`, `save query`, and `save resume` commands to the exact managed console. Before hold, it writes a durable pending-resume marker tied to the saved run, process identity, and a fresh attempt nonce. It attempts resume after a normal or failed fixture query, and an internal recovery call can send resume for that exact run after the Host data store is reopened. Dispatch alone retains the marker and blocks another hold; only a matching acknowledgement from the disposable fixture clears it in checks. Missing, stale, or mismatched acknowledgements leave the marker for review. The fixture checks run-scoped synthetic query evidence, bounded file names and sizes, rejected traversal and changed sizes, and resumed writes after interruption. There is still no production acknowledgement parser or held-snapshot publisher. Startup recovery and the fixed owner retry action now call only its exact-run resume path. Microsoft's [save command](https://learn.microsoft.com/en-us/minecraft/creator/commands/commands/save?view=minecraft-bedrock-stable) lists hold, query, and resume, while the [experimental LevelStorage API](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server-admin/levelstorage?view=minecraft-bedrock-experimental) describes snapshot file paths and sizes. Neither establishes the dedicated server's stable console query output format. There is no production parser, copy, or shared version; completion and live-capture flags remain false.

The [Factorio console reference](https://wiki.factorio.com/Console) documents `/server-save` as a server save command. The [multiplayer guide](https://wiki.factorio.com/Multiplayer) separately says headless servers autosave normally and save on exit. None of those statements identifies a completion signal for this running instance or proves its ZIP can be loaded elsewhere.

For **each game separately**, use a disposable staging world on a real Windows Host and Friend PC. Make a recognizable in-game change while the server runs, complete the candidate save, transfer and verify it on the Friend PC, load it with a newly configured Host, then gracefully restart and confirm the change remains. Record game/app versions, the exact completion signal, failed or interrupted attempts, and the direct-IP route. Enable that game's live capture only after the test passes and the adapter can stage an immutable, hash-verified snapshot without exposing a half-written world. Until then the interface offers no “Save and share now” action.
