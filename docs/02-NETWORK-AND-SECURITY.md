# Public connection and pairing

The owner may use direct public-IP access, an owner-installed private mesh, or an owner-managed advanced address. The companion API can request actions on the owner's PC, so every route uses the same strict controls. Keep the exposed surface to a small HTTPS API; keep the Host GUI and local owner settings on loopback.

## Connections

- The Friend app initiates the connection to the Host. The Host does not try to open an inbound connection to a Friend PC behind a home router.
- For the companion connection, only the Host PC may need an inbound router forward and Windows Firewall allowance for its configured HTTPS TCP port. A Friend joining that Host does not forward a port. A PC that also hosts its own server handles that separate Host route independently.
- The Host has a configurable TCP control port separate from each game's declared ports. No listener on a public interface is enabled by default. Explicitly display the bound address and port after the owner enables it.
- An Internet test must come from a Friend on another network. A localhost or same-LAN request is not proof that the public IP/port works. Detect and explain likely unroutable WAN/ISP NAT cases; do not silently alter the router or Windows Firewall.
- The owner can request a read-only outside TCP check of the configured Friend port through portchecker.io. Compare the checker's view of the caller's public IPv4 address with the pinned invite endpoint before accepting its port result. A positive current result may be labeled **Reachable outside network** without a connected Friend; a fresh authenticated heartbeat then takes precedence as **Friend connected**. A reachable TCP port is not proof of valid TLS pairing; the final acceptance test still needs a Friend PC on another network. Report checker failures as inconclusive, not closed.
- A failed outside TCP check means the route needs inspection; it does not prove which layer blocked it. Present the Host listener, invite/public/WAN address, inbound firewall, router forward, and ISP/shared-address NAT as separate checks. A Friend timeout should point to the Host route; certificate and invite rejection should point to identity and pairing instead. The outside checker is optional and is not part of the connection path.
- Host mode may use an outbound HTTPS request to ipify to display its current public IPv4 address. A successful lookup is only an address hint: it does not prove port forwarding, firewall access, game join, or Friend app reachability. No account or credential is sent; if the lookup fails or becomes stale, do not present it as a verified connection.
- **Private mesh** offers addresses read from active Tailscale or ZeroTier adapters, and **Advanced address** accepts an owner-selected IPv4 address for WireGuard or similar networking. Detection is read-only. TogetherServer does not install a client, request provider credentials, change policies, or promise provider plan terms. It has no built-in relay. TLS pinning, device credentials, assignments, and permissions remain mandatory over a mesh.
- The game network mode is a separate setting. Valheim's [official dedicated-server guide](https://www.valheimgame.com/support/a-guide-to-dedicated-servers/) states that the Steam backend normally needs the selected UDP port and the following port reachable (default 2456-2457), while its Crossplay backend uses a relay and does not require game-port forwarding. Neither mode supplies the companion-control connection.
- The Host reads Windows' active listener tables for the ports declared by the selected built-in game driver and for the companion TCP listener. `Open on PC` is local evidence only. `Friend reached` comes from a fresh authenticated heartbeat. Missing local listeners report `Opening`, `Closed on PC`, or `Unknown`; they are never promoted to public reachability. A real Friend game join remains separate evidence.

## Host identity and Friend credentials

- Host mode generates a TLS identity. Its certificate/private key stays on the Host in Windows-protected storage. An open pairing window has one current `TS3` code carrying the Host endpoint, full certificate fingerprint, server profile ID, random pairing secret, and bounded expiry; the owner shares it through a trusted channel. Friend mode pins that identity and refuses mismatches without a "skip certificate checks" button.
- The Host identity is stable independently of the advertised endpoint. Endpoint recovery begins from an existing saved connection and accepts a new endpoint only when its TLS certificate matches a currently accepted pin and the existing device credential authenticates. A replacement certificate is never trusted just because it appears at the new address.
- Certificate rotation is staged. The Host creates a next certificate, announces its fingerprint over the current pinned authenticated channel, then activates it while Friends accept the current and next/previous pins for a bounded grace period. Certificate expiries are visible on both sides. Already expired or offline clients use a new pairing flow.
- The Host's **Invite friends** action prepares the selected route, enables the HTTPS listener, and opens a window that defaults to one new PC for 30 minutes. The owner may choose a duration from 5 minutes to 24 hours, a limit from 1 to 25 PCs, and local approval for each activation. Closing pairing rotates and expires the code but preserves paired credentials. Revoking one PC affects only that credential. Emergency revoke closes the window and invalidates the credential lineage issued through that server code. Older `TS1`/`TS2` one-time invites and existing `TS3` codes remain decodable for migration; a pre-window `TS3` gets one bounded 30-minute migration window rather than indefinite reuse. `TS1` still needs a separate Host IP. No Friend IP is entered.
- Each Friend **device** gets a distinct 90-day random credential and an initial assignment containing only the server profile encoded by its `TS3` code. Through the loopback-only GUI, the Host may replace that assignment with any subset of saved profiles, including none, and independently allow Start, Stop, and fixed timer extension for each selected profile. Restart requires both Start and Stop; timer extension is off by default. Assignment without lifecycle permission still exposes that server's status and connection details. The Host validates every profile ID and checks assignment plus effective per-server permission for every status response and action. Host stores device credential hashes; Friend stores its credential and connection name through Windows-protected storage. Do not put codes or credentials in URLs, logs, screenshots, activity, or Git.
- A Friend renews its 90-day credential over the authenticated pinned connection before expiry. The Host retains the old hash for a ten-minute overlap, and a protected renewal receipt makes retrying the same renewal ID return the same new token after a lost response. Only hashes and the short protected receipt are stored by the Host; an expired or revoked credential cannot renew.
- Validate the credential, Host identity, request size, action kind, and permissions for every request. Bind lifecycle requests to an idempotency key so retries after a network timeout cannot start a second process.
- The owner can revoke one Friend device immediately. Its next request must fail clearly. An offline app learns about revocation when it reconnects.
- Rate-limit unauthenticated pairing by source IP, authenticated status/actions by device, and all traffic with a global Host backstop. Keep a structured redacted activity feed for pairing, access, remote actions, lifecycle, countdown, recovery, route, and backup-failure events. Retain at most 500 entries or 30 days, and never record credentials, invite codes, passwords, raw Custom scripts, player IPs, executable arguments, or private paths.

As of the project handoff, [Let's Encrypt supports public-IP certificates](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability), but they last about six days and need reliable automated renewal. Pinning the Host certificate in the manually shared password is the current direction for this app. The implementation must still verify the actual TLS and pairing behavior with two separate PCs; a local mock does not certify it.

## Remote disable and notices

`remoteControlsEnabled` is an owner-controlled switch separate from whether a game is running. When false, Host immediately denies **all remote Start/Stop requests** with a typed `RemoteControlsDisabled` result. Authenticated heartbeat/status may continue and includes `remoteControlsEnabled: false` and an optional owner notice for display. A Friend app online at the time shows it on its next poll; an offline Friend shows it on reconnect. If Host is unreachable, show Disconnected/Unknown, not a fabricated disable notice.

Per-Friend server assignments, permission changes, and revocation are checked by Host on each action even if the Friend UI has stale cards or buttons. A device requesting an unassigned profile receives `PermissionDenied` before lifecycle code runs. No Friend request may supply an executable, script, command line, working directory, world save path, or arbitrary settings update. Public input is a request for a fixed approved action only.

The one deliberate exception to another profile's assignment/Stop permission is the fixed **replace empty port conflict** action. It authorizes from Start permission on the requested assigned profile and reveals only the conflicting saved name and shared declared ports. It does not reveal the unassigned profile's join address or grant general Stop. Host denies it while remote controls are paused, while any conflicting count is positive or Unknown, or while the owner has an active **Add time** extension. A second exact-zero query occurs inside the lifecycle gate immediately before the existing graceful Stop path. Ordinary Start only returns the conflict and never invokes this action implicitly.

Remote Stop uses the selected built-in game driver's local occupancy evidence instead of player IDs. The server must be Ready and report exactly zero online players. Valheim first uses its local query. Only when a non-Crossplay query sends no reply may the driver use a complete join/leave history or periodic connection checkpoint from that run's own log; a malformed query or incomplete/contradictory log sequence remains Unknown. A positive, missing, malformed, timed-out-without-safe-fallback, or unsupported result denies the request. Host asks the same driver again under the lifecycle gate immediately before signaling Stop; a changed or unknown result sends no signal. The local owner Stop path deliberately remains available as the owner's override. Local count evidence does not prove public reachability, a particular Friend join, or saved-world integrity.

Automatic shutdown uses the same Host-only authority and final driver count. Friend apps receive a display deadline or blocker reason but cannot create or expire it. The loopback-only Host GUI may add an explicit number of minutes. With the optional `CanExtendTimer` permission, a Friend may submit only the fixed `extend` action; the Host applies its configured increment and per-countdown maximum, never a Friend-provided duration. Any positive or Unknown count cancels the deadline and all extension state. Friend connectivity and local game processes do not participate in the decision. A Host app restart begins a fresh observed idle window. The feature is off by default and never turns query silence into zero.

## Owner approval gates

This repository setup does not publish a listener, request a certificate, install a binary, or modify a firewall/router/DNS setting. During real deployment, stop and ask for the owner's explicit approval before changing public firewall/router/DNS configuration or requesting credentials. The owner must accept game terms and install any terms-gated dedicated-server binary personally. Do not send invites to friends from a tool without the owner's explicit authorization.
