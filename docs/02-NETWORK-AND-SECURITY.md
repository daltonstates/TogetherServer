# Public connection and pairing

The owner may use direct public-IP access, an owner-installed private mesh, or an owner-managed advanced address. The companion API can request actions on the owner's PC, so every route uses the same strict controls. Keep the exposed surface to a small HTTPS API; keep the Host GUI and local owner settings on loopback.

## Connections

- The Friend app initiates the connection to the Host. The Host does not try to open an inbound connection to a Friend PC behind a home router.
- For the companion connection, only the Host PC may need an inbound router forward and Windows Firewall allowance for its configured HTTPS TCP port. A Friend joining that Host does not forward a port. A PC that also hosts its own server handles that separate Host route independently.
- The Host has a configurable TCP control port separate from each game's declared ports. No listener on a public interface is enabled by default. Explicitly display the bound address and port after the owner enables it.
- An Internet test must come from a Friend on another network. A localhost or same-LAN request is not proof that the public IP/port works. Detect and explain likely unroutable WAN/ISP NAT cases; do not silently alter the router or Windows Firewall.
- The owner can request a read-only outside TCP check of the configured Friend port through portchecker.io. Compare the checker's view of the caller's public IPv4 address with the pinned invite endpoint before accepting its port result. A positive current result may be labeled **Reachable outside network** without a connected Friend; a fresh authenticated heartbeat then takes precedence as **Friend connected**. A reachable TCP port is not proof of valid TLS pairing; the final acceptance test still needs a Friend PC on another network. Report checker failures as inconclusive, not closed.
- Connection Doctor must keep its evidence ladder non-transitive: local listener, encoded address, outside TCP result, pinned/authenticated Friend heartbeat, local game readiness, and real game join are separate facts. Its coordinated Friend test may compare only post-start heartbeat receipt time and a fresh trusted server count against a local baseline. The local Acceptance Recorder may persist an owner's explicit check IDs only against a fingerprint of the current configuration; those records never become authentication, authorization, occupancy authority, player identity, or automatic acceptance. Friend mode presents saved access, Host TCP, pinned identity, device access, protocol, assignment, and a supported fixed game-endpoint check as separate stages. It probes only the current saved profile through existing fixed requests, and its copied report contains stage states rather than codes, credentials, pins, endpoints, addresses, IDs, names, or player identity. Both workflows offer navigation and read-only checks only; they never change firewall, router, DNS, mesh, or ISP state.
- A failed outside TCP check means the route needs inspection; it does not prove which layer blocked it. Present the Host listener, invite/public/WAN address, inbound firewall, router forward, and ISP/shared-address NAT as separate checks. A Friend timeout should point to the Host route; certificate and invite rejection should point to identity and pairing instead. The outside checker is optional and is not part of the connection path.
- Host mode may use an outbound HTTPS request to ipify to display its current public IPv4 address. A successful lookup is only an address hint: it does not prove port forwarding, firewall access, game join, or Friend app reachability. No account or credential is sent; if the lookup fails or becomes stale, do not present it as a verified connection.
- **Private mesh** offers addresses read from active Tailscale or ZeroTier adapters, and **Advanced address** accepts an owner-selected IPv4 address for WireGuard or similar networking. Detection is read-only. TogetherServer does not install a client, request provider credentials, change policies, or promise provider plan terms. It has no built-in relay. TLS pinning, device credentials, assignments, and permissions remain mandatory over a mesh.
- The game network mode is a separate setting. Valheim's [official dedicated-server guide](https://www.valheimgame.com/support/a-guide-to-dedicated-servers/) states that the Steam backend normally needs the selected UDP port and the following port reachable (default 2456-2457), while its Crossplay backend uses a relay and does not require game-port forwarding. Neither mode supplies the companion-control connection.
- The Host reads Windows' active listener tables for the ports declared by the selected built-in game driver and for the companion TCP listener. `Open on PC` is local evidence only. `Friend reached` comes from a fresh authenticated heartbeat. Missing local listeners report `Opening`, `Closed on PC`, or `Unknown`; they are never promoted to public reachability. A real Friend game join remains separate evidence.
- Owner diagnostics and support export remain on the loopback GUI surface and require the sensitive local header even though they are GET requests. They accept no arbitrary probe target, query, request body, or filesystem destination. The export uses an allowlist and defense-in-depth sanitization and size bounds: never include credential material or hashes, codes, passwords, protected blobs, scripts/arguments, full private paths, IP addresses or endpoints, certificate material, player/chat identity, raw server logs, worlds, or environment variables. Errors returned to the UI are fixed and must not reflect exception details or rejected secret values.
- Recent archived-session summaries are also loopback-owner-only GET data and require `X-TogetherServer-Local: 1`. The route resolves one saved Host profile, accepts only a 1-through-20 limit, and returns an allowlisted typed projection with no player names, chat, addresses, paths, credentials, passwords, world data, raw logs, scripts, or executable arguments. No companion/Friend history route or permission exists.
- Backup-vault copy and restore rehearsal are loopback-owner-only actions over a saved profile and completed backup ID. The vault destination comes only from the native owner folder picker; the browser and every companion request supply no path. The copy rejects app-data/live-world overlap and linked vault children, verifies the completed source and every copied hash, and leaves the local backup unchanged. A restore rehearsal uses owned disposable scratch storage and never swaps the live world.
- The loopback-owner-only Host move kit reuses a verified completed backup and stores only basic game/world/port details beside it. Destination inspection uses the native folder picker and hashes the entire payload before guiding a manual import. No credential, TLS private key, game password, or executable is included; a new Host identity and new Friend pairing are required.
- Factorio RCON uses a random per-profile Windows-protected password and a fixed local client for player count and `/quit`. No local browser or Friend contract accepts RCON text or the password. Because the game may listen beyond loopback, the configured RCON port must remain unforwarded and separate from the UDP game port.
- Update handoff requires a bounded hash-manifested local-state recovery checkpoint and revalidates it in the replacement helper. This does not weaken the existing payload SHA-256 or optional same-publisher Authenticode checks. Digest-only and development builds remain visibly distinct from a verified Windows publisher.

## Chat access and data

Chat sync uses the deliberately enabled Host HTTPS listener with the same pinned TLS identity, per-device credential, device rate limit, and assigned-server check as status. A separate owner-controlled room exclusion list permits removing a PC from one assigned server's chat while keeping its status and lifecycle permissions intact. Every sync rechecks current device access and room membership before returning content. A removed or expired device receives no new messages; a copied message cannot be recalled. A Friend can return only Host-signed accepted entries, and a new draft is attributed to the currently authenticated device rather than an identity supplied by the request. The Host never treats a chat message as a script, command, game count, saved-world version, or recovery decision. The public chat body is capped at 768 KiB, with at most 200 accepted entries, 20 drafts, and 500 characters per message. Protected local chat is deliberately excluded from support exports, activity messages, and raw logs. Direct exchange between Friend PCs while the Host is offline has no route in this design; a separate peer listener and its own reachability and authorization model would be required.

## Host identity and Friend credentials

- Host mode generates a TLS identity. Its certificate/private key stays on the Host in Windows-protected storage. Each saved server can have one current `TS3` code carrying the Host address, full certificate fingerprint, server profile ID, and random shared secret; the owner shares it through a trusted channel. The code remains active until the owner deliberately replaces it. Friend mode pins the Host identity and refuses mismatches without a "skip certificate checks" button.
- The Host identity is stable independently of the advertised endpoint. Endpoint recovery begins from an existing saved connection and accepts a new endpoint only when its TLS certificate matches a currently accepted pin and the existing device credential authenticates. A replacement certificate is never trusted just because it appears at the new address.
- Certificate rotation is staged. The Host creates a next certificate, announces its fingerprint over the current pinned authenticated channel, then activates it while Friends accept the current and next/previous pins for a bounded grace period. Certificate expiries are visible on both sides. Already expired or offline clients use a new pairing flow.
- The Host's **Invite friends** action prepares the selected route, enables the HTTPS listener, and copies the server's current code. It creates the code on first use and otherwise returns the same code with the current address and active Host identity. The code has no time or device-count window. Optional local approval can hold each newly connected PC. Removing one PC affects only that PC. **Replace code and remove old access** changes the secret and generation, removes access issued through the old code, and leaves other servers' codes and PCs untouched. Older `TS1`/`TS2` one-time invites retain their original expiry. Existing `TS3` codes remain decodable; their historical timestamp does not expire a server-scoped code because the Host's saved active code is authoritative. `TS1` still needs a separate Host IP. No Friend IP is entered.
- Each Friend **device** gets a distinct 90-day random credential and an initial assignment containing only the server profile encoded by its `TS3` code. Through the loopback-only owner API and persisted permission model, the Host may replace that assignment with any subset of saved profiles, including none, independently allow Start, Stop, fixed timer extension, and View logs for each selected profile, and set or clear a separate owner access deadline. The React permission editors expose the global and per-server action choices, including mixed exceptions. Status-only, Start-only, and trusted-helper presets submit all four reviewed global booleans in one local-owner request and explicitly clear per-server exceptions; Custom is display state for mixed or individual choices, not a wider permission. The separate deadline editor shows the canonical owner-access state, offers only the six reviewed durations plus Clear, and keeps explicit custom UTC input under Advanced with future/365-day validation and a local-time preview. Restart requires both Start and Stop; timer extension and View logs are off by default, including for legacy data. Start/Stop never implies View logs. Assignment without lifecycle permission still exposes that server's status and connection details, but not its log. Maintenance and the remote-lifecycle toggle are checked independently from View logs. The Host validates every profile ID and checks current owner access, assignment, and effective per-server permission for every status response, action, and log read; revocation and owner expiry each apply to the next request. Host stores device credential hashes; Friend stores its credential and connection name through Windows-protected storage. Do not put codes or credentials in URLs, logs, screenshots, activity, or Git.
  A separate one-hour or eight-hour temporary helper grant overlays all four permissions only for this PC's existing assignments. Every Host authorization reads the current deadline, so expiry or **End now** returns to saved permissions without relying on a Friend refresh. Revocation, owner-access expiry, maintenance, player-count, and remote-control gates still apply.
- A Friend renews its 90-day credential over the authenticated pinned connection before expiry. The Host retains the old hash for a ten-minute overlap, and a protected renewal receipt makes retrying the same renewal ID return the same new token after a lost response. Only hashes and the short protected receipt are stored by the Host; an expired, revoked, approval-pending, or owner-expired device cannot renew.
- Validate the credential, owner access deadline, Host identity, request size, action kind, assignment, and permissions for every request. Bind lifecycle requests to an idempotency key so retries after a network timeout cannot start a second process. Re-resolve the canonical device before queued lifecycle execution; never trust a `PairedDevice` object retained before the owner changed its deadline.
- The owner can revoke one Friend device immediately. Its next request must fail clearly. An offline app learns about revocation when it reconnects.
- Rate-limit unauthenticated pairing by source IP, authenticated status/actions by device, and all traffic with a global Host backstop. Keep a structured redacted activity feed for pairing, access, remote actions, lifecycle, countdown, recovery, route, and backup-failure events. Retain at most 500 entries or 30 days, and never record credentials, invite codes, passwords, raw Custom scripts, player IPs, executable arguments, or private paths.
- Remote log reads use bounded cursor polling rather than heartbeat payloads. `server-logs-v1` advertises the feature; a Friend service refuses a Host without that capability, and the Host endpoint also requires a compatible protocol header. The browser calls only the loopback Friend proxy, which adds the pinned credential internally. Both sensitive loopback log GETs require `X-TogetherServer-Local: 1`, including Host reads. The API accepts no path, glob, encoding, or source and resolves a saved profile to an owned managed-run operation. Each cursor carries only a bounded version/run/offset payload plus an HMAC made with a cryptographically random service-lifetime key; the key is never persisted or returned, signatures are compared in fixed time, and any tampering, fabricated offset, other-run token, or pre-restart token returns the same typed invalid/stale result. Host may read the exact active or latest retained run; a Friend may read only the exact active run, preventing a new assignment from exposing retained pre-assignment history. The public endpoint atomically rechecks current owner access, assignment, and the effective View-logs grant before reading and again before returning records. The Friend proxy rejects a Content-Length above 3 MiB, enforces the same cap while streaming when length is absent or false, preserves request cancellation/timeouts, and never includes oversized remote content in its typed failure. Explicit Valheim, Minecraft Java, and Minecraft Bedrock adapters verify the derived owned path and cap tail bytes, scanned bytes, records, and line length. Minecraft framing also prevents stdout/stderr content from forging record metadata. The shared sanitizer strips ANSI/control and directional-format characters before serialization. Friend output redacts or omits passwords, codes, bearer/token-like values, addresses, platform/player identifiers, chat/player names, and private paths. Host output may retain more game diagnostics but still redacts protected app secrets. Custom logs and unsupported adapters return typed states without remote file access. Owned run logs older than 30 days are pruned on startup, read, and new-log creation while a recorded active run is preserved. Minecraft console capture is capped and uses bounded nonblocking queues; sink failure switches to draining/discarding and never changes readiness, occupancy, Stop authorization, replacement, automatic shutdown, or process identity.

## Owner access deadlines

`AccessExpiresUtc` is nullable protected pairing metadata and is not the 90-day renewable credential expiry. Null means no owner deadline. At `HostUtcNow >= AccessExpiresUtc`, authentication returns HTTP 403 `AccessExpired` without profiles, activity, logs, operation details, credential material, or another secret. Heartbeat, status, Start, Stop, Restart, replacement, timer extension, player refresh, credential renewal, operation lookup, endpoint recovery, self-revoke, and server-log reads all use that boundary. The stored credential hash, invite lineage, assignments, and permission settings are not removed or revoked by expiry.

Only the loopback owner API may mutate the field. `PUT /api/local/devices/{deviceId}/access-expiry` accepts exactly one of Clear, an explicit UTC timestamp later than now and no more than 365 days away, or `OneHour`, `EightHours`, `OneDay`, `SevenDays`, `ThirtyDays`, or `NinetyDays`. It rejects ambiguous or malformed input, non-UTC offsets, past or excessively distant timestamps, unknown duration values, unknown devices, revoked devices, and all Friend-mode calls. There is no companion endpoint for setting this or another device's deadline. This is a single access cutoff, not general scheduling or arbitrary-expiry invitation support.

Local `DeviceView` includes the UTC deadline and derived expired flag. The bounded local activity feed and text audit record set, clear, and first-observed expiry transitions using only the device identifier and non-secret state; they never include credentials or invite codes. Approval pending is checked independently before owner expiry, renewable credential expiry remains its own typed denial, and revocation remains authoritative. The local owner may extend or clear an expired deadline without repairing, rotating, or recreating the credential.

As of the project handoff, [Let's Encrypt supports public-IP certificates](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability), but they last about six days and need reliable automated renewal. Pinning the Host certificate in the manually shared password is the current direction for this app. The implementation must still verify the actual TLS and pairing behavior with two separate PCs; a local mock does not certify it.

## Remote disable and notices

`remoteControlsEnabled` is an owner-controlled switch separate from whether a game is running. When false, Host immediately denies **all remote Start/Stop requests** with a typed `RemoteControlsDisabled` result. Authenticated heartbeat/status may continue and includes `remoteControlsEnabled: false` and an optional owner notice for display. A Friend app online at the time shows it on its next poll; an offline Friend shows it on reconnect. If Host is unreachable, show Disconnected/Unknown, not a fabricated disable notice.

Per-Friend server assignments, permission changes, and revocation are checked by Host on each action even if the Friend UI has stale cards or buttons. A device requesting an unassigned profile receives `PermissionDenied` before lifecycle code runs. No Friend request may supply an executable, script, command line, working directory, world save path, or arbitrary settings update. Public input is a request for a fixed approved action only.

The one deliberate exception to another profile's assignment/Stop permission is the fixed **replace empty port conflict** action. It authorizes from Start permission on the requested assigned profile and reveals only the conflicting saved name and shared declared ports. It does not reveal the unassigned profile's join address or grant general Stop. Host denies it while remote controls are paused, while any conflicting count is positive or Unknown, or while Host- or Friend-added shutdown time remains saved for the conflicting run. A second exact-zero query occurs inside the lifecycle gate immediately before the existing graceful Stop path. Ordinary Start only returns the conflict and never invokes this action implicitly.

Remote Stop uses the selected built-in game driver's local occupancy evidence instead of player IDs. The server must be Ready and report exactly zero online players. Valheim first uses its local query. Only when a non-Crossplay query sends no reply may the driver use a complete join/leave history or periodic connection checkpoint from that run's own log; a malformed query or incomplete/contradictory log sequence remains Unknown. A positive, missing, malformed, timed-out-without-safe-fallback, or unsupported result denies the request. Host asks the same driver again under the lifecycle gate immediately before signaling Stop; a changed or unknown result sends no signal. The local owner Stop path deliberately remains available as the owner's override. Local count evidence does not prove public reachability, a particular Friend join, or saved-world integrity.

Automatic shutdown uses the same Host-only authority and final driver count. Friend apps receive a display deadline or blocker reason but cannot create or expire it. The loopback-only Host GUI may add an explicit number of minutes while a Ready server has a reliable zero or positive count. With the optional `CanExtendTimer` permission, a Friend may submit only the fixed `extend` action under the same conditions; the Host applies its configured increment and per-server-run maximum, never a Friend-provided duration. Any positive or Unknown count cancels the current deadline, but already-added minutes remain saved in memory for that managed run and are applied to the next exact-zero idle window. Stopping/restarting the server, changing the idle wait, disabling automatic shutdown, lifecycle recovery, or restarting the Host app clears that extension state. Friend connectivity and local game processes do not participate in the decision. A Host app restart begins a fresh observed idle window. The feature is off by default and never turns query silence into zero.

## Owner approval gates

`game-requirements-v1` and `server-notices-v1` are additive capabilities. The requirements GET resolves only an assigned saved profile, requires a compatible protocol plus the exact feature capability header, rejects query/body input, and atomically rechecks current device access/assignment before and after the asynchronous metadata read. Responses are capped at 64 KiB, with at most 64 add-ons and 48-character versions; Host observation has a four-second deadline. The Friend proxy bounds declared and streamed bytes before JSON decoding, checks the returned scope/fields, and reauthenticates after local discovery. No profile path, protected state, credential, URL, executable choice, command or argument leaves through this response. Observed, owner-reported and manual sources stay distinct; unknown metadata is not a compatibility pass.

Every new local feature route requires the exact local header, rejects queries, enforces Host or Join role through the mode/update gate, and rejects GET bodies. Mutations use bounded streamed input and exact field/duplicate/type checks. Backup bookmark, weekly summary, game settings/list, owner notice and owner requirement mutations have no companion counterpart. Open game accepts only an assigned profile ID and an empty POST body, verifies fresh pinned authenticated access before and after read-only availability inspection, and dispatches one fixed reviewed URI on the explicit click. It never accepts a Friend-selected address/path/URI/argument or Host-supplied client command. Missing completed local Steam metadata refuses dispatch so no game installation is requested.

The notice response is attached only after current chat access checks and a final reauthorization following the protected read. Friends verify the owner room key, signature and monotonic revision; a signed clear cannot be undone by an older copy. Owner notice input is not part of chat sync. Notices remain excluded from logs/support/activity. Backup names/pins and weekly summaries reveal no world payload, raw logs, private path or player identity.

This repository setup does not publish a listener, request a certificate, install a binary, or modify a firewall/router/DNS setting. During real deployment, stop and ask for the owner's explicit approval before changing public firewall/router/DNS configuration or requesting credentials. The owner must accept game terms and install any terms-gated dedicated-server binary personally. Do not send invites to friends from a tool without the owner's explicit authorization.
