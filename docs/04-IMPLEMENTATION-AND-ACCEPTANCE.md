# Implementation order and acceptance

Keep the project small and deliver working vertical slices. Start implementation in the new chat; these documents are the handoff, not the implementation.

## Slice 1 — Local Host app and GUI

- Create one Windows .NET 10 app that shows bundled React/TypeScript assets in its own window over a loopback-only local API, with a clear Host/Friend mode switch. Build and publish without requiring Node at runtime.
- Add local settings for an approved server executable/profile, maximum concurrent managed servers (default 1), idle minutes (initially disabled), and remote-control disabled state. Keep secrets and worlds outside the repo.
- Implement fixed local Start, Stop, Health, and explicit empty-port-conflict replacement actions with a small purpose-built synthetic process fixture. Verify duplicate Start, one-writer-per-world, max count, named port conflicts taking precedence over the generic limit, process identity, crash/restart Unknown, and that Stop never kills an unrelated process.
- The GUI must show actual state, pending actions, and errors. Do not label a fixture or running process as a real Valheim server. This slice is accepted only after a Windows build, meaningful process tests, and a served React GUI check.

## Slice 2 — Friend mode and public-control protocol

- Add bounded owner-opened pairing windows, pinned Host TLS identity, Friend outbound heartbeat, saved Host endpoint, explicit per-friend server assignments, per-server Start/Stop/Extend permissions with global defaults, and typed remote actions. A code initially grants only its encoded server; only the loopback owner GUI may approve a waiting PC or reassign a paired PC to zero, one, or several current saved profiles. Use one small HTTPS listener; the Host GUI remains loopback-only.
- Implement the owner remote-control toggle and notice. Disabled remote Start/Stop must fail server-side immediately; status/heartbeat still communicates Disabled. Revoke one device and prove its credential stops working while another remains valid.
- Test retry/idempotency, invalid token, wrong certificate, wrong effective per-server permission, mixed global permission state, denial for a valid credential against an unassigned server, zero/one/multiple Host reassignment, unknown profile rejection, stale/Unknown heartbeat, Host restart, and at least two instances on separate local processes. Exercise pairing expiry/device limits, optional approval, close without revoke, per-PC revoke, emergency code revoke, rename, reachable and offline Forget, maintenance, redacted activity, and fixed timer-extension limits. Older unscoped credentials must migrate with no server access until the Host assigns them. These tests do not prove public Internet reachability.
- Test the everyday GUI path: new or copied world, world name and password in one compact setup, direct Start, bounded pairing-window creation/copy/close, immediate listener enable/disable, scoped revocation, and action-first Host/Friend cards. Verify the custom native minimize, maximize/restore, close, and important-event tray notification paths. Verify 1440x900, 768x1024, and touch-enabled 390x844 layouts without horizontal overflow. TS1 and TS2 per-device invites remain readable until expiry.
- Test remote Stop with disposable Valheim, Minecraft Java, and Minecraft Bedrock protocol fixtures: expose zero and positive online-player counts, deny positive and unknown counts, recheck after initial approval, and allow a permitted Friend Stop over HTTPS only at zero. This is parser, process, and policy evidence, not proof of a real game join or save.
- Test explicit port-conflict replacement with a Start-only Friend assigned only to the requested profile: ordinary Start reports the other saved name and shared ports without stopping it; positive/Unknown counts and a Host **Add time** extension deny replacement; an unextended zero-player conflict receives a second count check, graceful Stop, and then launches the requested profile without granting general Stop or exposing the other join address.
- Test the game-driver registry with Valheim, Java, Bedrock, an isolated synthetic driver, and fail-closed handling of unknown kinds. For each real driver, verify its declared ports, start-time conflict check, local listener diagnostics, readiness evidence, online-player count, and graceful stop. A local open port or count reply must not be recorded as public reachability.
- Test the explicit Custom driver separately: scripts stay Host-only and Windows-protected; the long-running Start wrapper retains verifiable process identity; Status/players uses bounded strict contract-v2 JSON and timeouts; local Stop requires the wrapper to exit; uncertified or mismatched counts never authorize lifecycle actions; and the complete owner certification proves zero/positive/zero, final-zero race protection, wrapper exit, restart, saved-change confirmation, persistence, and invalidation. Certified Custom remains owner-certified compatibility evidence, never official support for the selected game.

## Slice 3 — Real Valheim and friend smoke

- Use the owner-installed, owner-approved Valheim Dedicated Server. Verify the selected build, actual startup/readiness, game ports, graceful Ctrl+C-equivalent stop, save folder, and recognizable world change across stop/restart against [upstream guidance](https://www.valheimgame.com/support/a-guide-to-dedicated-servers/). Do not download or accept terms on the owner's behalf.
- Verify Valheim's real player count across zero, one, disconnect, and unavailable states, including the owned-log fallback on a private non-Crossplay server whose local query is silent. Confirm that partial log events remain Unknown and that Crossplay does not use the unvalidated fallback. A Friend Stop must be denied at one or Unknown and recheck zero immediately before Ctrl+C. Automatic shutdown must cancel its shared Host/Friend countdown at one or Unknown; later exact zero starts a full new window. Verify an owner-entered extension changes only the active deadline, then recheck zero immediately before Ctrl+C. No Host/Friend client-process setting or Friend heartbeat may gate the countdown. Keep automatic shutdown off for valued worlds until its separate real idle/save acceptance passes.
- With the owner's explicit approval, test the chosen public-IP control port from an actual Friend network and the game join path separately. Do not change public router/firewall/DNS settings automatically. A localhost test is not a public reachability pass.
- Record a real Friend start/stop permission test, disable notice, actual game client join, save, stop, restart, idle behavior, and Host recovery. Keep any missing external test marked **blocked**, not passed.

## V1 acceptance gate

V1 is accepted only when the owner can run the bundled Host app; every Friend requesting controls uses the bundled Friend mode; remote Start/Stop and disable/revoke work over the deliberately selected direct, private-mesh, or advanced route; max-concurrent and one-world writer rules hold; no remote or automatic action treats an unknown player count as zero; Valheim starts, reports a real player transition, accepts a real friend, stops gracefully, and preserves a recognizable world change through restart. Record exact versions, commands, screenshots/log excerpts with private details removed, and pass/fail/skip counts.

## External gates and data protection

The owner must handle game terms and deliberately initiate any Minecraft installation in the app, public router/firewall approval, credential exchange, and the real Friend/client test. Valheim installation remains an owner/Steam action. Continue independent code and local fixture testing while those are pending. Never delete or overwrite a real world for a test. Create isolated synthetic data under ignored `local-data/` and leave the owner's existing game install and worlds alone.

For candidate testing beside a stable install, use only the marked `--staging` instance. Acceptance requires simultaneous production/staging process evidence with distinct data and loopback/control ports, rejection of equal/nested/pre-populated roots, rejection of production save paths and existing-world import, no Windows startup or automatic-update mutation, and an unchanged fake production-world marker. Real Friend acceptance still requires the staging Friend app on another PC/network to authenticate to TCP 5132 (or its explicitly chosen staging port), followed by a separate real game join to the staging game's ports. Local synthetic evidence does not satisfy either external gate.

## Minecraft extension gate

Java and Bedrock have separate built-in drivers. Their fixture checks cover validated settings, TCP/UDP local status responses with online-player counts, positive-count Friend Stop denial, concurrent profiles with separate save folders, and fixed graceful console Stop. Setup checks cover bounded file detection, consent denial, fresh Java/Bedrock installs through synthetic HTTP responses, hashes, archive safety, and existing-world preservation. Before claiming real support for either edition, test an owner-installed server, zero/one-player status transitions, actual Friend join, recognizable world change after Stop/restart, the automatic-shutdown idle window, and the intended network route. Keep automatic shutdown off for valued worlds until that edition passes its real idle and save rule.
