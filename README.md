# TogetherServer

TogetherServer is one Windows app for hosting Valheim, Minecraft Java, Minecraft Bedrock, the Factorio and Terraria previews, or an owner-scripted custom game server and connecting to a friend's server. The same EXE runs on every PC. It opens a borderless native window with app-styled minimize, maximize, and close controls around its bundled interface; Node and the .NET SDK are needed only to build it.

## Install and open the app

For a normal PC, download and run `TogetherServer-Setup-win-x64.exe` from the [latest GitHub Release](https://github.com/daltonstates/TogetherServer/releases/latest). It installs for the current Windows user without an administrator prompt, creates a **TogetherServer** Start-menu shortcut so Windows Search can find it, and adds an uninstall entry under **Settings > Apps > Installed apps**. The build is currently unsigned, so Windows may show **Unknown Publisher**.

Setup optionally lets you choose a starting page, open TogetherServer at Windows sign-in, and close it to the tray. **Decide later** is the default and both Windows preferences start off. Skipping every choice still completes the install normally and leaves the existing in-app first-use guide available. Installer setup never installs or starts a game server, copies a world, opens a public listener, or changes firewall/router settings. Uninstall removes the app and its shortcuts but preserves `%LOCALAPPDATA%\TogetherServer`, including settings and managed worlds.

The portable `TogetherServer-win-x64.exe` remains available on the same release for people who do not want an installation. **Host** and **Join** are pages in the same running app; switching pages does not stop hosting or a Friend connection. Keep the app running while hosting or playing.

Use the gear in the app header to enable **Open at Windows sign-in** and **Close to tray**. Sign-in launches quietly in the Windows tray under your account. With Close to tray enabled, the window's X hides it while hosting and Friend checks continue. Double-click the TogetherServer tray icon to reopen it, or right-click it for **Open** and **Quit**. A normal manual launch also reopens the running app. Reopening restores a minimized window and recenters it when its prior bounds are no longer on any connected monitor. Quit still asks you to stop or resolve managed servers first. Both options are off until you enable them. The installer gives the app a stable location; when using the portable EXE instead, move it to its intended location before enabling startup.

Build a fresh unsigned production-mode EXE with `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1`. Use the development/staging package below when the stable app must remain open at the same time. The repository pins .NET in `global.json` and Node in `.node-version`.

## Develop beside the stable app

Use the explicit staging instance when friends need the stable app to keep working while a candidate is tested. Build and assemble it with:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/prepare-staging-package.ps1 -Build
```

The package is written to `local-data\staging-package`. Double-click the unmistakably named **TogetherServer DEVELOPMENT.exe**, or use its separate **DEVELOPMENT Host** and **DEVELOPMENT Friend** launchers. The filename itself selects the isolated staging instance, so opening the EXE directly cannot hand off to the running production app. The development process is also labeled in its native title, square **D** tray/taskbar icon, and bright orange **DEVELOPMENT / STAGING** in-app banner, which shows the active local-app and Friend-control ports.

Development/staging can run beside the normal app because it uses `%LOCALAPPDATA%\TogetherServer-Staging`, loopback UI port 5128, and Friend-control port 5132 by default; the normal app keeps `%LOCALAPPDATA%\TogetherServer`, ports 5127 and 5131, and its own process lock. Windows sign-in startup and automatic release updating are disabled for staging so it cannot replace or deregister the stable app.

Development begins with no production profiles, settings, credentials, managed runs, or worlds. Its own profiles, credentials, settings, and newly created worlds persist across development launches under `%LOCALAPPDATA%\TogetherServer-Staging`. That folder must be new and empty on first use, is permanently marked as development/staging, and cannot equal, contain, or sit inside the production data folder. The development API accepts only save paths inside that folder. Valheim creates a separate development world; existing production-world browsing/import is disabled. Minecraft development uses a separate in-app install and port defaults. Custom scripts are disabled because unrestricted owner scripts could reference production files. Do not manually copy production data into the development folder.

For a real friend test, the Host opens **Start TogetherServer DEVELOPMENT Host**, creates a separate development world, and sends the invite created by that development window. Each tester opens the same candidate with **Start TogetherServer DEVELOPMENT Friend**; their stable saved connections remain in the normal data folder. Test **Connect** from an actual Friend PC on another network, then test the game join separately. The development TCP 5132 route and development game ports (Valheim 2458-2459, Java 25566, Bedrock 19134-19135 by default) need their own owner-approved route. TogetherServer does not change firewall, router, DNS, or private-mesh configuration. A local listener or Host-side test is not proof that the Friend PC connected.

## App updates

The published production Windows app checks the [TogetherServer GitHub Releases](https://github.com/daltonstates/TogetherServer/releases) page at startup and every 30 minutes afterward; App settings can check again on demand. When a newer stable release is available, TogetherServer prompts once each time the app process opens and keeps an update message at the top of the app and in the notification menu. **Not now** closes only that launch's prompt. The update is never forced, and the persistent message remains until that version is installed. Development/staging stays offline from stable-app updates.

Choose **Update and restart** from the prompt, top message, or notification menu. TogetherServer downloads only the fixed `TogetherServer-win-x64.exe` asset from this repository's stable GitHub Release, bounds its size, verifies the release SHA-256 digest, and requires the file version to match the release tag. The helper repeats the hash checks immediately before and after replacement. If the installed app is Authenticode-signed, the candidate and helper must also have a valid signature from the same publisher public key. An unsigned installation can update without that publisher check; an invalid or unverifiable signature still disables updates rather than downgrading to unsigned trust. This avoids a paid signing dependency but means the GitHub repository, release metadata, and digest are the trust root rather than an independently verified publisher identity. Windows may continue to show Unknown Publisher for unsigned builds.

Stop any hosted server first; the app refuses to quit for an update while a managed run is active or unresolved. Before handoff it creates and verifies a bounded same-user checkpoint of top-level settings, protected access, and recovery state, tied to the current EXE hash, target version, and storage schema; a changed checkpoint aborts replacement. The helper keeps a `.previous` copy beside the actual running EXE, restores it if post-replacement verification fails, and reopens that same filename. Local settings, credentials, worlds, and completed backups stay in their existing data directory. The installer deliberately uses a writable per-user location so the same non-elevated updater works there. The UI labels the active trust as **Verified publisher**, **GitHub digest only**, **Signature rejected**, or **Development build**. A trusted publisher still requires an owner-provided signing certificate; this repository does not claim one for unsigned builds.

Release preparation requires a clean checkout, a new stable `<Version>`, an unused local and origin tag, an unused output directory, and [Inno Setup 6](https://jrsoftware.org/isdl.php) (`winget install --id JRSoftware.InnoSetup -e -s winget`). Run `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/prepare-github-release.ps1`. Without a signing thumbprint, the script prepares unsigned portable and installer EXEs and reports their `NotSigned` status, Windows Unknown Publisher warning, and GitHub-rooted update trust model. When trusted signing is available, pass `-SigningCertificateThumbprint CERT_THUMBPRINT` (or set `TOGETHERSERVER_SIGNING_THUMBPRINT`) with `signtool.exe`; signing then uses SHA-256 plus an RFC 3161 timestamp and fails closed unless Windows reports `Valid`. Both paths run the serial source and exact-app verification matrix, including the applicable update-replacement handoff, then build and smoke-test the installer against those exact app bytes. The four outputs are `TogetherServer-Setup-win-x64.exe`, `TogetherServer-Setup-win-x64.exe.sha256`, `TogetherServer-win-x64.exe`, and `TogetherServer-win-x64.exe.sha256` under `local-data\github-release\vVERSION`. The script refuses to replace an installed TogetherServer copy during the disposable installer smoke, overwrite an existing release directory, create a tag, or publish a release. After review, create the matching `vMAJOR.MINOR.PATCH` GitHub Release and attach all four files without renaming them.

## Host a server

1. On first use, choose **Host a server** or **Join a server**. Hosting starts a four-step guide: Game, World, Server app, and Review. For Valheim, choose **Create new** and name the world, or **Use existing** and copy a world found on this PC. An existing world is copied to a separate app-managed save folder; the source is never moved or overwritten.
2. Select the installed Valheim Dedicated Server if it was not found automatically, then review and choose **Save and start**. **Finish later** keeps the non-secret first-server draft on this PC; enter the game password again when resuming. Steam installation, updates, and game terms remain your actions.
3. Saved servers use compact cards with **Start server** or **Stop server** and **Invite friends** as the main actions. When a server is Ready, its Connection details appear directly on the card, outside **Technical details**. The server IP and Valheim game password are masked separately for stream safety; each has its own eye and **Copy** button, so showing or copying one does not expose the other. A shown value hides after 30 seconds or when the app loses focus. Connection exceptions appear inline; routine ports and diagnostics stay under **Technical details**. Use **Manage server** for editing, health checks, and recovery actions. **Friend access** opens named sections for Friend permissions, remote Stop, connection help, and advanced paths.
4. Choose **Invite friends** to copy that server's code. The first use creates the code and starts the secure Friend connection when needed. The same code remains available and can connect more PCs until the owner deliberately replaces it; it does not expire after a timer or stop after one PC uses it. The owner may require approval for each new PC. Every connected PC still receives separate revocable access and initially sees only the server whose code it used. Under **Friend access**, choose **Choose servers** to give a PC access to any combination of saved servers and independent **Start**, **Stop**, **Add shutdown time**, and **View logs** permissions. Add-time and View-logs access both default false; Start/Stop never grants either one. Apply **Status only**, **Can start**, or **Trusted helper** when one reviewed permission set fits every assigned server; applying a preset updates all four global permissions atomically and clears per-server exceptions. A mixed or individually edited device remains **Custom**. Remove one PC's access separately. **Replace code and remove old access** is the deliberate recovery action when a code was shared by mistake: it replaces the code and removes access created through the old one without affecting PCs connected through other server codes. Existing `TS1`, `TS2`, and `TS3` formats remain readable for migration.

Each paired PC can also have a separate owner-defined access deadline. **Friend access** shows **No deadline**, **Access ends** with the exact local date/time and relative time, or **Access expired** independently from approval, revocation, and the renewable credential expiry. The compact editor offers 1 hour, 8 hours, 1 day, 7 days, 30 days, 90 days, and **Clear deadline**. Its Advanced path accepts an explicit UTC date/time in the future and no more than 365 days away, previews the exact UTC value and its local conversion, then uses one Save action. Assignments and Start/Stop/Extend/View-logs permissions do not change when the deadline changes.

The editor calls only the loopback Host API `PUT /api/local/devices/{deviceId}/access-expiry`, which accepts exactly one of `{ "clear": true }`, an explicit future UTC `{ "accessExpiresUtc": "...Z" }`, or `{ "duration": "OneHour" }`. The reviewed duration values are `OneHour`, `EightHours`, `OneDay`, `SevenDays`, `ThirtyDays`, and `NinetyDays`. Friend mode, malformed or non-UTC timestamps, past or excessively distant deadlines, unknown durations, unknown devices, and revoked devices are rejected. No companion mutation route exists.

Owner access expiry is distinct from the renewable 90-day credential. At the exact deadline, the next authenticated heartbeat, status, Start, Stop, Restart, replacement, timer extension, player refresh, credential renewal, operation lookup, endpoint recovery, self-revoke, or server-log request returns HTTP 403 with code `AccessExpired`. The credential hash, assignment, and permissions stay intact so the local owner can extend or clear the deadline; an expired Friend cannot use the companion API to change its own or another device's deadline. Approval-pending, revocation, assignment, permission, and credential-expiry checks remain separate fail-closed states.

Friend mode presents typed `AccessExpired` as access deliberately ended by the Host owner, not as an unknown connection or revoked/expired credential. It explains that the owner can extend or clear the deadline and that the saved Host connection remains, so a new invite is not required.

The Host detects an outbound public IPv4 address to fill the game and app addresses. This is an address hint, not a reachability test. **Open on PC** means Windows sees a local listener. **Test Friend app port from internet** under **Friend access → Connection help** makes a read-only TCP check through [portchecker.io](https://portchecker.io/docs), which sees the current public IP and tests the Friend app port without receiving an invite or credential. A positive result shows **Reachable outside network** until an authenticated heartbeat takes precedence as **Friend connected**. The TCP result still does not prove pinned pairing or a game join. A failed test means the router, firewall, or ISP route needs attention. The app shows the current LAN address to use as the router forwarding target. Keep the Host app running, and forward its configured Friend app **TCP** port (default 5131) to that LAN address and the same port. **Friend connected** means a recent authenticated heartbeat, which by itself does not prove the Friend is on another network. Game joining is a separate test with separate game ports. TogetherServer does not change firewall, router, or DNS settings. Valheim Crossplay uses its relay, so its game status reports relay readiness instead of claiming router forwarding. Custom endpoints, bind IP, game paths, and the server concurrency limit live under clearly labeled **Advanced** settings.

**Settings → Connection help** includes Connection Doctor. It keeps the local listener, server-code address, outside TCP route, authenticated Friend heartbeat, local game readiness, and real game join as separate evidence stages. **Test with a Friend** captures a fresh post-start heartbeat and server-reported count change, then asks the two people to confirm the intended join and a recognizable saved change after graceful restart. The **Acceptance Recorder** can retain explicit owner confirmations for the exact game, world, executable, port, and route fingerprint; changing that setup makes them stale. These confirmations are not authentication, player identity, occupancy authority, or automatic proof. Friend mode has its own Connection Doctor for saved access, Host TCP, pinned identity, device access, protocol, assignment, and a supported fixed game-endpoint check. Its copied report excludes codes, credentials, pins, endpoints, addresses, IDs, names, and player identity.

Use **Settings → Diagnostics** (or **Preflight & diagnostics** in the Attention Center) for read-only owner checks before asking for support. Select a saved server to review its saved setup, exact managed-process state, driver/player observation, declared local ports, and latest assigned-Friend heartbeat alongside the app listener, last owner-requested route check, recovery state, and update state. These checks reuse the existing Host authorities and never start, stop, repair, or probe an arbitrary target. **Copy report** and **Download JSON** create the same bounded redacted UTF-8 report in memory with the fixed name `TogetherServer-support-report.json`; it contains typed summaries and log metadata, not credentials, codes, passwords, protected blobs, scripts/arguments, full private paths, addresses/endpoints, certificate material, player/chat identity, raw logs, worlds, or environment variables.

The owner may instead choose **Private mesh** and select an address from a user-installed Tailscale or ZeroTier adapter, or choose **Advanced address** for an owner-managed WireGuard or similar route. Adapter detection is read-only: TogetherServer does not install a network client, request its credentials, change policy, or promise a provider's plan terms. The same pinned TLS identity, per-device credential, server assignments, and action permissions remain mandatory on every route. There is no built-in relay.

Built-in server profiles can optionally enable **Restart after an unexpected server exit** and **Back up after each confirmed graceful Stop** under Advanced server settings. Crash recovery is off by default, applies only after that exact process was previously Ready and is definitively absent, waits 1, 5, then 15 minutes, and suspends after the third failed launch. A recorded Stop intent is never treated as a crash. PID reuse, executable mismatch, or process-access failure remains Unknown and keeps the world blocked.

Rolling backups are also off by default. After the exact process exits gracefully, TogetherServer copies only the driver's reviewed save directory into staging, hashes every file, atomically marks the completed backup, and enforces the owner's retention and free-space reserve. The Host-only **World Safety Center** also shows retained bytes and backup-drive free space, can create a labeled manual checkpoint only while the server is definitively Offline, and can re-hash any completed backup without touching the live world. **Copy to vault** copies an already completed backup to an owner-selected folder, rejects linked app/live-world destinations, verifies every transferred hash, and retains the local copy. Choose an external or network location for another-device protection. **Test restore** restores into disposable app scratch storage, verifies it, deletes the scratch copy, and never swaps the live world. **Safe restart** first confirms graceful exit, requires either the successful rolling checkpoint or a new offline manual checkpoint, and starts again only after that checkpoint succeeds; failure leaves the server offline. Restore still requires Offline, verifies the completed manifest, and takes a pre-restore snapshot before replacing the save directory. Friends cannot list, create, verify, rehearse, export, restore, delete, or browse backups. Custom profiles are excluded until a later explicit save-only-folder design. Real-game save/restart acceptance is still required before relying on these features for a valued world.

The selected Host server's **Sessions** tab shows a compact bounded history of archived exact managed runs. A new summary records only state TogetherServer owned at archival time: run/game identity, known start and end, derived duration, whether Ready was observed, typed outcome, crash-recovery scheduling, the last and peak trusted server-reported player observations, and the rolling-backup result. Legacy archives show unavailable fields instead of inferred values. These counts are observations, not proof of who joined, a successful game join, or world/save integrity. Session history is local-owner-only; Friends have no history endpoint or permission.

The Host **Players** tab shows the current trusted count, driver source, observation freshness, empty-server deadline/reason, and Host/Friend split of saved added time. Its recent history stores only count transitions, never player identities. Unknown or stale evidence remains visibly fail-closed. The Attention Center reports bounded app-data, backup, log, and save-drive space warnings; CPU count and app memory are visible details only and never authorize Start, Stop, replacement, or shutdown. Under **Settings → App**, **Keep Windows awake while hosting** is opt-in and requests only Windows idle-sleep prevention while an exact managed process is running; it is cleared when that process is gone, does not block deliberate sleep, and does not promise uninterrupted hosting. After a long suspend/resume polling gap, readiness, player count, and the active countdown are invalidated until a fresh observation; saved added-time credit is retained. If the app session was interrupted, startup reattaches only to an exact recorded process or offers a deliberate **Resume hosting** through the normal Start checks; it never starts a game automatically.

The local data directory carries an explicit storage-schema version. Storage schema 2 adds the owner access deadline to protected pairing state. On first open, this build advances a schema-1 directory marker to 2 before writing any schema-2 pairing snapshot, then migrates the protected pairing snapshot without deleting devices, invite lineage, assignments, permissions, or renewal receipts. A migration interrupted after the marker write is completed by the next schema-2 start. A schema-1 binary rejects that directory at startup instead of ignoring the authorization field; rolling back therefore requires restoring a complete pre-migration data backup with its matching schema-1 marker. Manually lowering the marker or mixing v1 and v2 state is unsafe and unsupported. This build also rejects an unknown newer schema.

If TogetherServer cannot parse a state file, it moves the original into `quarantine` and records a persistent recovery notice instead of silently overwriting it. Damage to lifecycle-authoritative settings, managed-run identity, crash-recovery state, restore state, or the schema marker blocks new Start, Restart, replacement, automatic shutdown, and crash-recovery work. A safe local Stop or archive of a still-authoritative recorded process remains available. The Host owner must review the notice, confirm that no unrecorded TogetherServer-managed game server is still running, and explicitly acknowledge recovery; acknowledgement keeps the quarantined evidence for review. Corrupt pairing material is disabled locally and legacy credentials are not silently restored. This protects control state only and does not prove that a real game world is healthy or restorable.

## Host server files and add-ons

Open a saved server's **Files** tab to open its existing server, world, log, backup, and supported add-on folders. The tab lists the active configuration and player-administration files for that game. It can edit reviewed text files in the app or open them in Notepad. Java and Bedrock player lists are checked as JSON; active Minecraft, Factorio, and Terraria configuration is checked again before Start. The in-app editor requires an exact file version, maintenance, Offline state, and a successful world checkpoint before Save or Undo. Opening Notepad gives the owner direct file access, so use **Reload file** after saving there.

**Prepare changes** pauses Friend lifecycle controls before checking players. A managed run is stopped only after a fresh trusted count of exactly zero, checked again inside the lifecycle gate. The app then makes a complete offline setup checkpoint. After editing or importing, Start the server, check its health and a real game join, and use **Finish maintenance** to record that check and resume Friend controls. If Stop, checkpoint, or restore cannot be confirmed, maintenance stays on. An interrupted complete setup restore blocks Start until the owner retries a complete setup restore.

Complete setup checkpoints include the driver's reviewed world directory, existing reviewed configuration files, and managed add-on files with an inventory. A backup that could not capture the full setup is labeled world-only and cannot be selected as a complete setup restore. Restore verifies both parts, makes a pre-restore checkpoint, applies the world and configuration while Offline, and attempts rollback if configuration restore fails. Setup metadata is protected for the same Windows user; a vault copy or Host move to another Windows account remains a world transfer and needs fresh local configuration and pairing.

Factorio supports owner-selected local mod ZIPs in a per-server mod folder, an enabled list, version checks, and one Undo. The fixed driver passes [Factorio's documented mod-directory and server-settings options](https://wiki.factorio.com/Command_line_parameters). Bedrock supports owner-selected local `.mcpack` behavior and resource packs copied into the selected world, with an enabled list and one Undo. Active shared server packs outside that world are shown as external and prevent a complete setup checkpoint; see [Bedrock's dedicated-server pack layout](https://learn.microsoft.com/en-us/minecraft/creator/documents/bedrockserver/getting-started?view=minecraft-bedrock-stable) and [pack manifests](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/addonsreference/packmanifest?view=minecraft-bedrock-stable). Factorio and Terraria can create per-server settings files using their [server settings format](https://raw.githubusercontent.com/wube/factorio-data/master/server-settings.example.json) and [dedicated-server config option](https://terraria.wiki.gg/wiki/Dedicated_Server). The game version and enabled add-on set appear beside Friend requirements; a detected game update requires owner review before Start. Java remains the official vanilla server JAR; Valheim and Terraria mod loaders have no reviewed import path.

The log viewer can filter likely startup, configuration, and add-on problems. The copied support report includes only bounded configuration availability, add-on counts, version, and review status, never file contents, package names, or paths. These local and fixture checks do not establish a real mod load, Friend join, or save integrity.

## Host Minecraft Java or Bedrock

Choose **Minecraft Java** or **Minecraft Bedrock** in the Host setup, then choose **Use an existing server** or **Install a new official server**. TogetherServer searches its own installs, your Desktop, Documents, Downloads, and bounded common Minecraft folders on local drives and reads `server.properties` for the world name and port. Java discovery is intentionally stricter than filename or launch-manifest detection: it lists only an official `server.jar` installed by TogetherServer whose TogetherServer-written provenance record and SHA-1 still match, and Start repeats that validation. A renamed, manifest-shaped, modified, or third-party JAR is rejected. **Browse server folder** can locate another prepared folder but does not bless an arbitrary JAR; raw paths stay under **Manual setup**. TogetherServer does not rewrite an existing configuration or world.

- **Install in the app:** Enter a world name and port, review the linked Minecraft EULA and Microsoft Privacy Statement, check the consent box, then choose **Install Java server** or **Install Bedrock server**. The app fetches the latest official server into a new private folder, never over an existing world. Java also fetches a matching Eclipse Temurin runtime and records `eula=true` only after your explicit consent. The Java JAR and runtime are checked against official metadata hashes and sizes; Bedrock's official download list currently supplies no digest, so the app validates its HTTPS source and ZIP layout. Save setup and choose **Start server**. The installed server binaries are not bundled with TogetherServer.
- **Existing Java:** Reuse a Java server folder only when it retains the TogetherServer provenance written during an earlier in-app official install and its `server.jar` still matches that recorded hash. Choose its Java runtime, review Minecraft's terms yourself, and keep `eula=true` in that folder. For an arbitrary or manually downloaded JAR, use **Install a new official server** instead; TogetherServer does not infer trust from JAR shape. [Official Java server download](https://www.minecraft.net/en-us/download/server).
- **Existing Bedrock:** Choose `bedrock_server.exe` in its folder. TogetherServer reads `server-portv6` and `enable-lan-visibility` too, including the default discovery ports when LAN visibility is on. [Official Bedrock server setup](https://learn.microsoft.com/en-us/minecraft/creator/documents/bedrockserver/getting-started?view=minecraft-bedrock-stable) and [properties](https://learn.microsoft.com/en-us/minecraft/creator/documents/bedrockserver/server-properties?view=minecraft-bedrock-stable).

TogetherServer checks for a local Java server-status reply or Bedrock RakNet status reply before showing **Ready**, and displays the online/max player count returned by that reply. This proves a local game response, not a Friend join. Each managed run also captures bounded Java or Bedrock stdout/stderr into that operation's app-owned log through a bounded asynchronous console host. The capture host keeps the game's stdin on its isolated Windows console, so Local Stop still sends only the fixed `stop` command to the exact recorded process and waits for exit. If that helper explicitly reports that no game process was created and its exact identity is confirmed exited, TogetherServer removes only that failed run so the owner can retry; a missing handshake, possible game identity, or any ambiguity leaves the run unresolved and blocks another writer. Log capture or display failure never changes readiness, player count, Stop authorization, or process identity. Friend Stop is available only when a fresh status reply reports zero players, and the count is checked again immediately before the stop command. The current Minecraft evidence uses disposable process fixtures; test the real installed editions, client joins, and recognizable world changes before relying on them for a valued world.

Choose **Factorio**, name the server, and use **Browse and copy save** on an existing `.zip`. TogetherServer makes a verified per-profile managed copy and never hosts from, moves, or overwrites the original. Choose an owner-installed `factorio.exe`; TogetherServer does not download the game or accept terms. The fixed driver launches only that managed save with the saved UDP game port and a random Windows-protected RCON password. Do not forward the RCON port because Factorio may listen on network interfaces.

This preview has fixture evidence for fixed launch, authenticated zero/positive counts, guarded graceful `/quit`, exact process identity, backups, vault copy, and restore rehearsal. ## Updates, maintenance, and moving Hosts

The Host's World Safety Center offers an offline game-update checklist, a verified backup, vault copy, and restore rehearsal. Changing a selected game executable or Java server JAR invalidates earlier owner acceptance confirmations. The maintenance guide pauses remote actions, waits for a trusted zero-player count before its Stop button, makes an offline checkpoint, then leads through restart and Connection Doctor. Friend cards include game-specific Join steps. A paired PC can receive one or eight hours of temporary helper permissions within its existing server assignments; expiry or **End now** restores its saved permissions.

The selected Host server's **Files** tab opens its existing server, save, TogetherServer log, and backup folders in Windows File Explorer. Minecraft Java and Bedrock point **Server app** at the prepared server folder and **World and saves** at that edition's selected world. Bedrock also shows its shared behavior-pack and resource-pack folders when present. Other built-in games show the installed server folder and their managed save folder; a missing folder stays unavailable instead of being created by a button. The vanilla Minecraft Java driver does not load a modded server JAR, and the current Factorio and Terraria drivers do not select an explicit mod directory or external config file, so the Files tab does not imply mod support for them.

The same tab can read and edit the active Minecraft `server.properties` or an existing Valheim `adminlist.txt`, `bannedlist.txt`, or `permittedlist.txt`. Only the local Host can use these routes. Begin maintenance and stop or resolve the managed server first; each change requires an exact file-version match, validates the Minecraft world name and game port against saved setup, completes an offline world checkpoint, and keeps one Windows-protected prior file version for **Undo**. Undo also requires maintenance, Offline status, a matching current file, and another checkpoint. Linked, missing, oversized, or non-UTF-8 files are not edited in the app. Start the server afterward, check its health, and confirm a real join and recognizable saved change before ending maintenance. World backup restore still follows its existing save-only scope; the protected single-file Undo handles a changed config file.

To move to another Host PC, stop the old server, make a fresh backup, and choose **Prepare move kit** beside it. The kit contains a verified world backup and basic server details, without game binaries, passwords, saved Friend access, or TLS keys. On the new PC choose **Inspect move kit**, copy its `payload` into a fresh offline game-server save location without overwriting an existing save, choose the locally installed game server, and pair Friend PCs again. Test a real join and recognizable saved change before retiring the old Host.

## Host another game with custom scripts

Choose **Custom game** for an advanced Host-only script profile. Enter the game and server names, an existing working/save directory, the primary and any additional TCP/UDP ports, then three PowerShell actions:

- **Start** launches the real server and must keep its own PowerShell process alive until that server exits.
- **Status and players** must finish within four seconds and output exactly one JSON object with `state` (`Ready`, `Starting`, or `Failed`) plus optional `detail`, `onlinePlayers`, `maxPlayers`, and `players` fields.
- **Stop** must finish within 15 seconds after asking the game to save and exit; the Start process must then exit within 90 seconds.

The app supplies `TOGETHERSERVER_ACTION`, `TOGETHERSERVER_PROFILE_ID`, `TOGETHERSERVER_WORLD_ID`, `TOGETHERSERVER_WORKING_DIRECTORY`, `TOGETHERSERVER_GAME_PORT`, and `TOGETHERSERVER_MANAGED_PID` environment values. Script bodies are protected with the current Windows account and are never sent to Friends. Scripts run with everything that Windows account can access, so use only code you wrote or reviewed.

Friends may request Start only by the already saved profile ID. They cannot submit script text, paths, arguments, or environment values. Custom status/player data remains display-only until the owner completes the built-in live certification: TogetherServer must observe zero → positive → zero, safely stop the exact tracked wrapper, restart the same world, observe the owner rejoin, and receive explicit confirmation that a recognizable saved change survived. A successful certification is Windows-protected and fingerprint-bound to all three scripts, the world ID, normalized save/working directory, declared ports, and Custom contract v2. Only that exact configuration can use guarded Friend Stop, Restart, empty-server replacement, or automatic shutdown. This is labeled **owner-certified Custom control**, not official built-in support. See the [game support catalog](docs/08-GAME-SUPPORT-CATALOG.md) for the evaluated built-in backlog.

## Join a friend's server

On your own PC, open the same EXE and choose **Join**. Paste the server code and choose **Connect**. The saved connection keeps its own pinned Host certificate and credential and initially shows only that code's server. If approval is required, it stays visibly pending until the Host approves that PC locally. If the Host later assigns more saved servers, they appear without another code. Saved Host connections can be renamed or forgotten. Forget first asks a reachable Host to revoke this PC; offline Forget removes the protected local credential and warns that the Host should revoke the stale device. Selecting another connection does not pause heartbeats or anything hosted on this PC. When a server is Ready, its masked Connection details appear on the Friend card. Request **Start**, guarded **Stop**, or **Restart** when allowed. Per-server maintenance remains visible but denies all remote lifecycle and replacement actions. The Friend card receives the Host's current server-reported count, shutdown deadline, durable operation progress, and redacted activity; no local game path or running-game check is needed.

Host identity is independent of its advertised IP. If the owner changes routes or addresses, use **Connection identity and recovery** on the saved Friend connection: the new endpoint is accepted only when the already pinned Host certificate and existing device credential both succeed there. Host certificates rotate through a staged next pin distributed over the current authenticated channel; Friends temporarily accept both pins. Device credentials renew to another 90-day credential with a short retry overlap. Expired or offline clients pair again. Friend cards can send the built-in Valheim or Minecraft query from that PC and report **Game endpoint answered from this PC**; that check never claims a player joined.

The Attention Center and native tray show important pairing, permission, remote-action, lifecycle, countdown, player-count, recovery, route, backup, and expiry events. Repeated matching events collapse behind a count, and reviewed categories link to the relevant server tab or Settings section without embedding commands in activity data. **Clear activity** hides everything currently shown for the selected Host or saved Friend connection; later events appear normally. Clearing is a local display preference and does not delete the Host's retained activity record. The bounded local feed never stores credentials, invite codes, passwords, Custom script bodies, player identities, or player IP addresses.

Current `TS3` server codes include the address, exact initial server, shared secret, and pinned Host identity. Their older timestamp field remains in the format for compatibility, but the current Host decides whether the saved server code is active; a current server code does not expire with time. Older `TS1` and `TS2` per-device invites remain readable only until their original expiry, and because they do not carry a trustworthy server scope, the Host must explicitly assign their connected PC before it can see or control a server. `TS1` also needs the Host IP under **Using an older invite?**.

### Who checks the router?

The PC running the **Host** page is the Host. A Friend using **Join** makes an outbound connection and does not forward a port for that connection. The Host enables Friend connections by creating or copying a server code, then checks the HTTPS TCP port under **Friend access → Connection help**. **Open on PC** checks only the local connection. The optional internet test checks whether that TCP port can be reached from outside; a failed result calls for checking the address in the server code, Windows Firewall, router forwarding to the Host PC's shown LAN address, and possible ISP/shared-address NAT. An inconclusive result does not establish whether the port is open. The final check is **Connect** on a Friend PC on another network. A secure-identity or server-code error after a TCP connection has a different cause; do not bypass the identity check.

Joining the game uses separate ports. For Valheim Crossplay, the game's relay means no game-port forwarding. For Valheim Steam, Minecraft Java, and Minecraft Bedrock, the game Host may need to forward the game ports shown on its server card. A local game-port check does not prove an outside player can join. The Friend does not forward game ports unless that Friend also hosts a different server. TogetherServer does not require a cloud relay and does not change router or firewall rules itself.

## Stop and player safety

TogetherServer warns during setup when a saved game-port plan overlaps another saved server and suggests the next non-overlapping configured port when it can. This is guidance only; Start remains the authority. Immediately before launch, the Host serializes the request, compares every driver-declared protocol/address-family/port against every managed run, and checks whether Windows can bind the ports. A conflict names the running server and shared ports, and the second server is not launched.

After a Friend receives that conflict, an explicit **Stop empty server and start this one** action may replace the conflicting server. The Friend needs Start permission for the requested server, but does not need access to or Stop permission for the conflicting server. The Host reveals only the conflicting server name and shared ports, not its join details. Replacement is denied unless every conflict is Ready and reports exactly zero players, and the count is checked again inside the same lifecycle gate immediately before graceful Stop. It is also denied while any Host- or Friend-added shutdown time remains saved for that run. Remote controls must remain enabled. The first Start request never stops another server automatically.

The owner can always request local Stop. It rechecks the recorded process ID, creation time, and executable path. Valheim receives Ctrl+C; Minecraft receives its fixed `stop` console command. The app waits for exit and never force-kills an unrelated process. A timeout leaves the run recorded for review.

Every Ready built-in game server shows the latest online-player count on both the Host and Friend cards. Valheim first uses its Steam-compatible query reply on the configured port plus one. If a non-Crossplay Valheim server sends no query reply, TogetherServer can instead derive the count from that run's own server log: a complete join/leave sequence updates it, including one that begins while the server is still reaching Ready, and Valheim's periodic `Connections` line resets it. A partial or contradictory sequence, malformed query reply, or silent Crossplay query is **Player count unavailable**, never zero. Java and Bedrock use the same local status replies that establish Ready. The round-arrow beside the count lets either the Host or an assigned Friend request an immediate fresh Host observation; the resulting canonical status is returned to that Friend and shared by later Host/Friend refreshes.

A Friend Stop request is allowed only when that current count is exactly zero. TogetherServer repeats the query inside the lifecycle gate immediately before signaling Ctrl+C or the fixed Minecraft `stop` command. If the count becomes positive or unknown, no stop signal is sent. The owner can always make a local Stop decision from the Host page, including while players are online. [Valheim's dedicated-server guide](https://www.valheimgame.com/support/a-guide-to-dedicated-servers/) documents the two-port range and Ctrl+C stopping.

Friend Start, Stop, Restart, and empty-server replacement are durable Host operations. The Host returns an operation ID immediately, persists the request before executing it, and exposes Pending, Running, Succeeded, Failed, or Interrupted through normal Friend status refreshes. Retrying the same request ID cannot execute it twice. A Host restart marks unfinished work Interrupted and never automatically replays a Stop, Restart, or replacement. Restart requires both Start and Stop permission, completes a guarded graceful Stop before starting the same saved profile, and does not Start if Stop fails.

Game observations are supervised once per managed run about every three seconds and shared by the Host UI, Friend status, and countdown logic. When a built-in server is Starting or Ready without a count, one observation cycle makes two short bounded retry probes before publishing Unknown; later cycles continue trying. A cached observation older than ten seconds becomes Unknown. The final Stop/replacement check never trusts that cache: it probes again while holding the serialized lifecycle gate.

Automatic shutdown is off by default. The owner can enable it and choose a 1-to-1440-minute wait under **Friend access → Stop & timer**. When a Ready server reports exactly zero players, the Host and every assigned Friend see the same live **Stops in** countdown. The Host polls while supervising about every three seconds, and Friend status refreshes about every five seconds. Otherwise every Ready card says **Timer not running** and explains that the feature is off, players are online, or the server count is unavailable. Friend heartbeats and game clients do not gate the timer. The Host can add shutdown time while a Ready server reports a reliable zero or positive count. The optional **Add shutdown time** permission is off by default and lets a Friend add only the Host-configured fixed increment, up to the Host-configured maximum for that server run; no arbitrary duration crosses the Friend API. A player or unavailable count cancels the current deadline, but added minutes stay saved and are applied in full when the same managed run next reaches zero. Stopping/restarting the server, changing the idle wait, disabling automatic shutdown, lifecycle recovery, or reopening TogetherServer clears that in-memory extension state. At expiry, the Host obtains the count again inside the lifecycle gate before using only the game's existing graceful Stop path. It never force-kills a timed-out server. Reopening TogetherServer starts a fresh countdown because the app cannot prove the server stayed empty while it was closed.

The local protocol fixtures prove count parsing, countdown reset, the final zero-player check, and graceful synthetic Stop. They do not prove a real Friend join or saved-world integrity. Test each owner-installed game, an actual zero/one/disconnect transition, graceful Stop, and a recognizable world change after restart before relying on remote or automatic Stop with a valued world.

The selected Host server has a **Logs** workspace tab. It tails a bounded recent page, follows later records by an integrity-protected exact-run cursor, keeps a capped client history, and offers pause/resume, manual refresh, and severity/category/contains filters. Cursor tampering, fabricated offsets, cross-run reuse, and reuse after a Host-process restart fail with the existing typed invalid/stale state. Polling stops when the viewer is hidden. Host may read the exact active run or the latest retained owned run; owned run logs older than 30 days are pruned on startup, read, and new-log creation unless they are still active. A Friend card shows **View logs** only when that exact assigned server has the separate permission and the Host advertises `server-logs-v1`. Friend reads are proxied by the local Friend service with its protected credential, capped while streaming before JSON decoding, and restricted to the exact active run, so a newly assigned Friend cannot read retained history from before assignment. Assignment, View-logs permission, revocation, and owner access expiry are checked again before an asynchronously read response is returned. Older peers receive a typed update-required state. Friend records omit protected secrets, addresses, platform/player identifiers, player/chat names, and private paths; both Host and Friend records strip control/ANSI sequences and cap lines and batches. Callers never submit a path, source, glob, encoding, or arbitrary argument. Custom and other unsupported game logs are not remotely exposed. These display records are diagnostic only and never replace the separate player-count evidence used by remote Stop, replacement, or automatic shutdown.

## Developer checks

The build includes disposable generic, Valheim, Minecraft, and Factorio process fixtures. Isolated checks keep their data under ignored `local-data/` and do not use a real game binary or world. The preferred command builds one candidate and then runs the source checks plus packaged companion, served, and hidden desktop checks serially against that exact EXE:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify-release.ps1 -Build
```

The script first proves that the committed NuGet lock is usable in locked mode and confirms the candidate version and SHA-256 before and after the matrix. Its dedicated **Core remote journey** launches the packaged Host and Friend as separate processes and requires authenticated connect, remote Start, occupied Stop denial, zero-player graceful Stop, typed closed-port detection, and saved-access reconnect after both apps restart. This is loopback/fixture regression evidence, not a public-network or real-game-join claim. The desktop smoke runs hidden in the tray by default so it does not take over the active screen. Pass `-SkipDesktop` only when a non-desktop environment cannot host WebView2, and run `checks/desktop-smoke.ps1 -Interactive` separately only for an attended visible check. The real replacement handoff runs for signed candidates with SHA-256 plus same-publisher verification and for ordinary unsigned candidates with SHA-256 verification.

The Host lifecycle uses reviewed built-in game drivers plus one explicitly advanced local custom-script driver. Valheim, Minecraft Java, Minecraft Bedrock, Factorio, Terraria, and Custom game appear in setup; the synthetic driver exists only for isolated checks. See [adding a game](docs/07-ADDING-A-GAME.md) for the process, port, readiness, stop, and security contract.
